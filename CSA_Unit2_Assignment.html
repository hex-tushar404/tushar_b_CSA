1. Assignment Objective

Create a rigorous IAM structure on AWS that demonstrates the Principle of Least Privilege. The specific requirements are:

  1. Create distinct IAM Groups — Admins, Developers, Auditors — each with custom policies scoped to only what that role needs.
  2. Enforce Multi-Factor Authentication (MFA) for the Admin group.
  3. Create a custom IAM Role that allows an EC2 instance to access S3 securely without hardcoded credentials.

2. Introduction to IAM & Least Privilege

What is AWS IAM?

AWS Identity and Access Management (IAM) is a service that helps you securely control access to AWS resources. IAM lets you create and manage AWS users, groups, roles, and their permissions using policies (JSON documents).

Key IAM Concepts

ConceptDescription
UserAn individual identity with long-term credentials (password, access keys).
GroupA collection of users that share the same permission policies.
RoleAn identity with temporary credentials, assumable by services (e.g., EC2) or users.
PolicyA JSON document that defines Allow/Deny statements for specific actions and resources.
MFAMulti-Factor Authentication adds a second layer of sign-in security.
Instance ProfileA container for an IAM Role that can be attached to an EC2 instance.

Principle of Least Privilege

The Principle of Least Privilege states that every user, service, or process should be granted only the minimum permissions necessary to perform its intended function — nothing more. This minimises the blast radius of compromised credentials and accidental changes.

4. Terraform Code – Detailed Walkthrough

4.1 Provider Configuration & S3 Bucket

We configure the AWS provider with a specific region and create a demo S3 bucket with all public access blocked:

terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

# S3 bucket that the EC2 role is allowed to access
resource "aws_s3_bucket" "app_bucket" {
  bucket = var.s3_bucket_name
}

resource "aws_s3_bucket_public_access_block" "app_bucket" {
  bucket                  = aws_s3_bucket.app_bucket.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
Least Privilege: All public access is blocked on the S3 bucket using aws_s3_bucket_public_access_block — the bucket is private by default.

4.3 Custom Policies – Principle of Least Privilege

4.3.1 Admins Policy

Admins get broad operational access to EC2, S3, IAM management, CloudWatch, and Logs. However, they are explicitly denied billing, AWS Organizations, and account-level actions — so even the "admin" tier is not root-equivalent. 

data "aws_iam_policy_document" "admins_policy" {
  statement {
    sid    = "AllowServiceAdministration"
    effect = "Allow"
    actions = [
      "ec2:*",
      "s3:*",
      "iam:Get*",
      "iam:List*",
      "iam:CreateUser",
      "iam:CreateGroup",
      "iam:CreateRole",
      "iam:AttachUserPolicy",
      "iam:AttachGroupPolicy",
      "iam:AttachRolePolicy",
      "iam:PutUserPolicy",
      "iam:PutGroupPolicy",
      "iam:PutRolePolicy",
      "cloudwatch:*",
      "logs:*"
    ]
    resources = ["*"]
  }

  statement {
    sid       = "DenyBillingAndOrgChanges"
    effect    = "Deny"
    actions   = ["aws-portal:*", "organizations:*", "account:*"]
    resources = ["*"]
  }
}

resource "aws_iam_policy" "admins_policy" {
  name        = "AdminsLeastPrivilegePolicy"
  description = "Admin permissions scoped away from billing/org root actions"
  policy      = data.aws_iam_policy_document.admins_policy.json
}

resource "aws_iam_group_policy_attachment" "admins_attach" {
  group      = aws_iam_group.admins.name
  policy_arn = aws_iam_policy.admins_policy.arn
}
Key Design: Even the Admins group does not have *:* root-level access. Billing (aws-portal:*), AWS Organizations (organizations:*), and account management (account:*) are explicitly denied.

4.3.2 Developers Policy

Developers can run/stop/terminate EC2 instances (only in the configured region) and read/write only the app S3 bucket. IAM actions are explicitly denied to prevent privilege escalation. 

data "aws_iam_policy_document" "developers_policy" {
  statement {
    sid    = "EC2DevAccess"
    effect = "Allow"
    actions = [
      "ec2:Describe*",
      "ec2:RunInstances",
      "ec2:StartInstances",
      "ec2:StopInstances",
      "ec2:TerminateInstances",
      "ec2:CreateTags"
    ]
    resources = ["*"]
    condition {
      test     = "StringEquals"
      variable = "aws:RequestedRegion"
      values   = [var.aws_region]
    }
  }

  statement {
    sid    = "S3DevBucketAccess"
    effect = "Allow"
    actions = [
      "s3:GetObject",
      "s3:PutObject",
      "s3:ListBucket"
    ]
    resources = [
      aws_s3_bucket.app_bucket.arn,
      "${aws_s3_bucket.app_bucket.arn}/*"
    ]
  }

  statement {
    sid       = "DenyIAMAccess"
    effect    = "Deny"
    actions   = ["iam:*"]
    resources = ["*"]
  }
}
Least Privilege highlights:
  • EC2 access is region-locked via a Condition block.
  • S3 access is scoped to only one specific bucket (ARN-based).
  • IAM actions are explicitly denied — Developers cannot create users, change policies, or escalate privileges.

4.3.3 Auditors Policy

Auditors receive read-only access across IAM, S3, EC2, CloudTrail, and AWS Config — enough for compliance review, zero write/modify access. 

data "aws_iam_policy_document" "auditors_policy" {

    effect = "Allow"
    actions = [

      "iam:List*",

      "s3:List*",

      "cloudtrail:DescribeTrails",
      "config:Describe*",
      "config:Get*",
      "config:List*"

    resources = ["*"]
  }
}

4.4 MFA Enforcement for Admins

An additional policy is attached to the Admins group that denies almost every action unless the caller has authenticated with MFA. Users can still manage their own MFA device so they are not permanently locked out. 

data "aws_iam_policy_document" "require_mfa" {
  statement {
    sid       = "AllowViewAccountInfo"
    effect    = "Allow"
    actions   = ["iam:GetAccountPasswordPolicy", "iam:ListVirtualMFADevices"]
    resources = ["*"]
  }

  statement {
    sid    = "AllowManageOwnMFA"
    effect = "Allow"
    actions = [
      "iam:CreateVirtualMFADevice",
      "iam:DeleteVirtualMFADevice",
      "iam:EnableMFADevice",
      "iam:ResyncMFADevice",
      "iam:ListMFADevices",
      "iam:GetUser",
      "iam:ChangePassword"
    ]
    resources = [
      "arn:aws:iam::*:mfa/${aws:username}",
      "arn:aws:iam::*:user/${aws:username}"
    ]
  }

  statement {
    sid       = "DenyAllExceptListedUnlessMFAed"
    effect    = "Deny"
    not_actions = [
      "iam:CreateVirtualMFADevice",
      "iam:EnableMFADevice",
      "iam:GetUser",
      "iam:ListMFADevices",
      "iam:ListVirtualMFADevices",
      "iam:ResyncMFADevice",
      "sts:GetSessionToken"
    ]
    resources = ["*"]

    condition {
      test     = "BoolIfExists"
      variable = "aws:MultiFactorAuthPresent"
      values   = ["false"]
    }
  }
}

resource "aws_iam_policy" "require_mfa" {
  name        = "RequireMFAForAdmins"
  description = "Denies all actions for Admins unless authenticated with MFA"
  policy      = data.aws_iam_policy_document.require_mfa.json
}

resource "aws_iam_group_policy_attachment" "admins_mfa_attach" {
  group      = aws_iam_group.admins.name
  policy_arn = aws_iam_policy.require_mfa.arn
}
How MFA enforcement works: The DenyAllExceptListedUnlessMFAed statement uses NotAction and a condition on aws:MultiFactorAuthPresent = false. If the user has NOT used MFA, all actions except MFA self-management are denied.

4.5 EC2 → S3 IAM Role (No Hardcoded Credentials)

A custom IAM Role is created that EC2 instances can assume via an Instance Profile. This enables secure S3 access without storing any access keys on the instance. 

# Trust policy: allow EC2 service to assume this role
data "aws_iam_policy_document" "ec2_assume_role" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["ec2.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "ec2_s3_role" {
  name               = "EC2-S3-Access-Role"
  assume_role_policy = data.aws_iam_policy_document.ec2_assume_role.json
}

# Scoped S3 access — only the app bucket
data "aws_iam_policy_document" "ec2_s3_access" {
  statement {
    sid    = "AllowScopedS3Access"
    effect = "Allow"
    actions = [
      "s3:GetObject",
      "s3:PutObject",
      "s3:ListBucket"
    ]
    resources = [
      aws_s3_bucket.app_bucket.arn,
      "${aws_s3_bucket.app_bucket.arn}/*"
    ]
  }
}

resource "aws_iam_policy" "ec2_s3_access" {
  name        = "EC2-S3-Scoped-Access"
  description = "Allows EC2 instances assuming this role to read/write only the app bucket"
  policy      = data.aws_iam_policy_document.ec2_s3_access.json
}

resource "aws_iam_role_policy_attachment" "ec2_s3_attach" {
  role       = aws_iam_role.ec2_s3_role.name
  policy_arn = aws_iam_policy.ec2_s3_access.arn
}

resource "aws_iam_instance_profile" "ec2_s3_profile" {
  name = "EC2-S3-Access-Profile"
  role = aws_iam_role.ec2_s3_role.name
}
Security benefits:
  • No access keys or secrets are stored on the EC2 instance.
  • The role uses temporary credentials that AWS automatically rotates.
  • S3 access is scoped to only the app bucket's ARN — a compromised instance cannot reach unrelated buckets.

5. Deployment Steps

  1. Clone the repository and navigate to the project: 
    git clone <repository-url>
cd iam-least-privilege-project
  2. Create terraform.tfvars with a globally unique bucket name: 
    s3_bucket_name = "kaveri-iam-unit2-demo"
  3. Initialise Terraform (downloads the AWS provider plugin): 
    terraform init
  4. Preview the plan: 
    terraform plan
  5. Apply the configuration: 
    terraform apply
    This creates 17 AWS resources: 3 IAM groups, 5 IAM policies, 4 policy attachments, 1 IAM role, 1 role-policy attachment, 1 instance profile, 1 S3 bucket, and 1 public access block.

7. How Least Privilege is Enforced – Summary

Group / Role Permissions Granted Restrictions / Denies
Admins EC2, S3, IAM management, CloudWatch, Logs Billing, Organizations, Account actions denied; MFA required for all actions
Developers EC2 (run/stop/terminate in one region), S3 (one bucket only) IAM actions explicitly denied; S3 scoped to specific bucket ARN; EC2 region-locked
Auditors Read-only: IAM Get/List, S3 Get/List, EC2 Describe, CloudTrail, Config Zero write/modify access anywhere
EC2-S3 Role S3 GetObject, PutObject, ListBucket on one bucket Scoped to specific bucket ARN; uses temporary credentials via Instance Profile
Each tier gets progressively fewer permissions: Admins > Developers > Auditors. Even Admins cannot touch billing or root-level account operations, and they must use MFA. The EC2 role has the narrowest scope — only three S3 actions on a single bucket.

8. Conclusion

This project successfully demonstrates the implementation of a rigorous IAM structure on AWS following the Principle of Least Privilege:

  • Three distinct IAM groups (Admins, Developers, Auditors) were created, each with custom policies that grant only the minimum necessary permissions.
  • MFA enforcement was applied to the Admins group using a deny-unless-MFA policy, adding a critical second factor of authentication.
  • A custom IAM Role with Instance Profile enables EC2 instances to access S3 securely without any hardcoded credentials, using temporary credentials that AWS rotates automatically.
  • The entire infrastructure was defined as Infrastructure as Code (IaC) using Terraform, ensuring repeatability, auditability, and version control.

The deployment was verified via the AWS Console, with all 17 resources created successfully. Screenshots confirm the creation of groups, policies, roles, the S3 bucket, MFA assignment, and IAM user creation by an admin.
